# AITeam v0.14.0

「管理專案」視窗（`ProjectManagerForm`）版面重新設計。

## 為什麼改

原本的「管理專案」視窗只是一排一排的欄位堆疊，欄位之間沒有分組、也沒有
視覺上的段落感，使用者不容易一眼看出「這幾個欄位是一組的」。先前已經跟
專案負責人討論過一版試作畫面（卡片分區、編號段落標題、可折疊的進階設
定），這次照那個設計實作。

這屬於一個獨立的、看得到的功能改善（介面重新設計＋新增可編輯的進階欄
位），不是接續上一個未解 bug 的修正，所以照版號規則升 `VERSION` 的 Y 碼
（0.13.1 → 0.14.0），`BUILD` 歸零。

## 改了什麼

- 版面改成卡片分區：「基本資訊」「GitHub Repo」「專案在 Repo 內的位置」
  各自是一張獨立的圓角卡片，每張卡片標題前面有一個藍色圓形編號（1/2/3），
  跟先前試作畫面的設計一致。
- GitHub Repo 卡片新增一個淺灰底的「Repo 資訊」小方塊，把 Repo 名稱、本
  機位置、目錄來源整理成清楚的幾行，取代原本單一段落文字。
- 「專案在 Repo 內的位置」的目前選擇狀態，也改成淺灰底提示方塊，跟 Repo
  資訊方塊風格一致。
- 新增「進階設定」卡片（預設收合，點一下標題展開／收合），裡面放三個原
  本完全沒有畫面、只能靠程式自動計算或需要手動改設定檔的欄位：
  - **版本檔路徑**（原本只會自動偵測 Repo 根目錄下有沒有 `VERSION` 檔）
  - **Tag 前綴**（原本只會自動用專案名稱產生，例如 `cyaccounting-v`）
  - **合併方式**（Merge commit／Squash／Rebase，原本永遠固定是
    Merge commit）
  
  這三個欄位現在都可以直接在畫面上看到、改，空白時維持原本的自動判斷
  規則（不會因為改版面就改變舊專案的既有行為）。
- 「已登錄專案」清單、按鈕樣式也統一改用跟主畫面一致的圓角卡片、配色。

## 保留不變的部分

所有原本的功能邏輯（載入 Repo、瀏覽 Repo 目錄樹、儲存專案、移除登錄、
忙碌狀態鎖定按鈕等）完全沒有改變，只是換了外觀跟版面配置，操作方式跟
之前一樣。

## Build 1（同一版號的第二次修正，未升版號）

實測 v0.14.0 後回報兩件事：AI 狀態的三張卡片格式跟畫面配置需要調整，以
及「進階設定」那三個欄位其實跟共用規則衝突或已經沒有用了。這些都屬於
同一批「管理專案」改版試作後的第一輪修正，`BUILD` 從 0 加到 1，`VERSION`
不變。

- **AI 狀態合併成一張卡片**：原本 GPT/Codex、Claude、Gemini 各自是一張
  獨立的圓角卡片，改成一張卡片裡面三列，欄位對齊成「名稱、燈號、狀態、
  說明、本次使用」的表格排版（用 `TableLayoutPanel` 統一欄寬，保證三列
  對齊）。原本每張卡片各自畫一次邊框，這也是先前「左半邊卡片右緣被切
  到」在這三張卡片上出現的原因之一；改成一張卡片、只畫一次邊框後，這
  三張卡片的裁切問題也一併消失（左側其他卡片是否還有同樣問題，仍待實
  測，尚未處理）。
- **拿掉「版本檔路徑」「Tag 前綴」「合併方式」三個可編輯欄位**：跟共用
  規則對照後確認：
  - 版本檔規則已經寫死在共用規則裡（一律是專案根目錄的 `VERSION`），
    讓使用者能改反而可能設定出違反規則的值，所以拿掉，`ChangeTaskService`
    直接固定讀寫 `VERSION`。
  - Tag 前綴只剩顯示用途（AITeam 早就不會自動打 tag），改成任務執行時
    自動用「專案名稱-v」產生，不再需要使用者事先設定或儲存。
  - 合併方式不再讓使用者選，`ChangeTaskService` 合併 PR 時一律用
    merge commit，拿掉 `ResolveMergeFlag` 與對應的 squash／rebase 選項。
  - `ProjectEntry` 對應移除 `VersionFile`、`TagPrefix`、`MergeStrategy`
    三個欄位；既有登錄檔裡如果還留著這幾個舊欄位，重新儲存專案時會被
    自然清掉，不影響原本的專案登錄資料。
  - 原本「進階設定」卡片的位置，改成一個唯讀的「版本升號規則（參考）」
    說明區塊，把共用規則裡的版本升號邏輯整理成幾行文字放在那裡，方便
    使用者查看，但不能在這裡修改。

## Build 2（左半邊被裁切問題的真正修正，未升版號）

Build 1 之後實測，左半邊被裁掉的範圍反而變大：原本只有卡片邊框被切到一
點點，變成連「管理專案」「重新檢查」按鈕、輸入框的捲軸都被切掉。這次從
兩張截圖（視窗化 vs 最大化）比對後，找到了真正的成因，前面兩次的猜測
（DPI 縮放時機、邊框畫太外面）都是錯的。

### 真正的成因

WinForms 的 `TableLayoutPanel`，如果宣告了 `ColumnCount = 1` 卻**沒有明確
加上任何 `ColumnStyles`**，那一欄的預設型態是 `AutoSize`——意思是「內容
需要多寬，這一欄就多寬」。這種欄位有兩個特性：

1. 空間有剩的時候，它會撐滿容器（所以視窗最大化時畫面完全正常）；
2. 空間不夠的時候，它**不會跟著縮**，而是維持內容需要的寬度，整塊內容
   就超出容器右緣，被容器裁掉（所以視窗縮小時右緣被切）。

主視窗裡有五個這種「單欄但沒設定欄寬」的版面容器（最外層、左半邊、AI
狀態區、右半邊、目前任務卡片），左半邊整個內容因此是照「內容需要的寬度」
排版，而不是照實際可用寬度排版。

這也解釋了為什麼 Build 1 反而更嚴重：Build 1 把 AI 狀態改成一列五欄
（名稱＋燈號＋狀態＋說明＋本次使用），這一列需要的寬度比原本三張直排卡
片大很多，於是整個左半邊被撐得更寬，溢出得更多，連按鈕和捲軸都被切到。
也解釋了為什麼「強制重新排版」那招完全沒用：這不是排版時機問題，是算出
來的數字本來就是錯的，重算幾次結果都一樣。

### 修法

- 所有單欄版面容器都明確加上 `ColumnStyle(SizeType.Percent, 100F)`，讓欄
  寬永遠等於容器實際寬度，視窗變窄時內容跟著縮，不再溢出。主視窗、專案
  管理視窗、Plan Gate 對話框都一併補上。
- 幾個會「用文字長度決定最小寬度」的標籤改成可壓縮（填滿剩餘空間、過長
  自動縮寫成 `…`）：AI 狀態的說明欄、專案卡片的 Repo／本機位置、左下角
  的提示文字。否則就算欄寬正確，這些標籤仍會把整塊內容撐寬。
- 移除 Build 1 之前加的「顯示後把視窗寬度加 1 再改回來」強制重排版程式
  碼——那是基於錯誤判斷加的，實測無效，留著只會讓視窗開啟時閃一下。

## Build 3（版面修好後的下一輪回饋修正，未升版號）

Build 2 實測確認左半邊裁切問題已解決。這一輪處理同一批回饋剩下的項目。

- **AI 狀態的說明欄不再縮寫成 `…`**：Build 2 為了不讓文字撐寬版面，把說明
  欄設成過長就縮寫，結果變成「本次工作會自...」看不懂。這些字本來就是要給
  人看的，改成用小一級的字（8.5pt）在欄寬不夠時自動折成兩行；同時把名稱欄
  與狀態欄的右側留白從 18px 縮到 12px，多讓出一些寬度給說明欄。
- **畫面左上角版號會跟著 Build 跳**：之前 `AITeam.App.csproj` 自己寫死一份
  版號（`0.14.0`），跟 repo 根目錄的 `VERSION`／`BUILD` 是兩套來源，改了
  `BUILD` 畫面也不會變。現在改成 csproj 直接讀 `VERSION` 與 `BUILD` 組出
  版號，畫面依共用規則顯示成 `V0.14.0 Build 3`（Build 為 0 時只顯示
  `V0.14.0`）。以後升版只要改那兩個檔案，不需要再同步 csproj。
- **「已登錄專案」清單改成小卡片**：這是 v0.14.0 試作畫面原本就有、但當時
  沒做到的部分。清單改用自繪項目，選中的項目是一塊圓角淺藍底、文字轉成
  強調色粗體，取代 Windows 預設的整條藍色反白。
- **執行進度／結果的字再小一級**：9.5pt 改成 9pt。

## 尚待實機驗證

這個改版是根據程式碼推理＋先前的試作畫面設計完成，這個環境沒辦法實際
在 Windows 上開啟視窗檢查，需要使用者實測後回報排版、間距是否正常。
