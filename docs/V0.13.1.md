# AITeam v0.13.1

跟這次的治理討論直接相關：**Change task 完成合併後，AITeam 不再自動幫目標
專案打正式版 tag。**

## 為什麼改

`docs/PIPELINE_REDESIGN.md` §5.1 原本的設計是：合併完 PR 之後，AITeam 直接
在正式分支的合併 commit 上打一個版號 tag（例如 `v0.12.1`）並推上 GitHub。
這個設計是在 governance 2.0/2.1 之前就有的。

governance 2.0/2.1 幫 AITeam 自己訂了「正式發布（tag + GitHub Release）
必須由使用者明確觸發，不能因為一般合併就自動發生」的規則，但當時只處理了
AITeam 自己的 GitHub Actions（`build-windows.yml`/`release-windows.yml`）。
沒注意到 AITeam 的 change task pipeline，本身也會對**任何**它管理的專案
（包含 AITeam 自己，如果之後把 AITeam 登錄成自己的專案）做一樣的事——
每完成一個任務就自動蓋一次正式版號，而大部分任務其實只是過程中的修改，
不需要每次都變成一個「正式版」。

跟專案負責人確認後，原則統一為：**版號數字（VERSION／BUILD）照常在每次
任務完成、合併時更新，但 tag／Release 這個「正式發布」的身分，永遠由使用
者另外明確觸發才建立**——不管目標專案是 AITeam 自己還是其他 managed
repository，一視同仁。

## 改了什麼

- `ChangeTaskService.RunAsync`：合併 PR 之後，移除自動建立 git tag、推送
  tag 的步驟。現在流程就停在「合併完成、同步本機」，不再多做正式化的
  最後一步。
- `ChangeTaskResult` 拿掉 `Tag` 欄位（不再有意義，因為不會自動建立）；
  `MainWindow` 顯示的完成訊息也跟著改成只顯示版本號。
- PR 內文與進度訊息裡，還是會顯示「未來正式發布時建議的 tag 是什麼」，
  純粹給人看的資訊，不代表已經建立。
- 補上 `PROJECT_RULES.md` §7 的一個缺口：原本只講不自動發布 GitHub
  Release，沒有明講不自動打 tag，這次一起講清楚（詳見
  `GOVERNANCE_CHANGELOG.md` 2.2.0）。

## 目前還沒做的事（先誠實記錄）

現在如果要正式把 CYAccounting 這類「AITeam 管理的其他專案」標成某個正式
版本，AITeam 沒有內建的按鈕可以做這件事了（跟 AITeam 自己有
`release-windows.yml` 不一樣）。如果之後需要，屬於一個新功能，要另外討論
設計。目前只能請使用者自己手動在 GitHub 上建立 tag／Release，或之後再請
AITeam 加上對應功能。
