# AITeam v0.10.0

Fourth implemented step of `docs/PIPELINE_REDESIGN.md` (§4.6, §4.3): a stale-evidence
reminder for Repair, and a bounded dispute mechanism so a false-positive review
finding doesn't force a speculative edit.

## Changes

- **Stale-evidence reminder.** `BuildRepairPrompt` now tells the Repairer that
  the Scout report and plan it's holding were produced at the start of the
  task, the code may have changed since (from its own earlier implementation
  or repair rounds), and to re-check the actual current file contents before
  editing rather than trusting the old description. This doesn't re-run Scout
  (the Repairer already has full read access to the live worktree) — it's a
  one-line nudge against a specific, previously-observed failure mode.
- **Bounded repair dispute.** The Repairer can now respond with
  `AITeamRepairStance: DISPUTE` plus a Traditional-Chinese rationale instead of
  always being forced to make a speculative edit, for cases where it believes
  the Challenge/Final Review finding is a false positive. When it does:
  - no file changes are required that round (`VerifyWorkingTreeAsync`'s "there
    must be a diff" check is skipped for a dispute round)
  - the same Final Reviewer re-adjudicates with the dispute reasoning added as
    context (`BuildDisputeReviewPrompt`)
  - if the reviewer is convinced, verdict flips to PASS and the task proceeds
    normally (version reconfirm → commit → formalize)
  - if the reviewer still disagrees, the dispute is rejected and the loop
    continues to the next round exactly as before — no round budget was
    skipped, and repeated disputes still eventually hit `max_repair_rounds`
    and fail safely with the worktree preserved
- `RunWriteAsync` now returns the implementer/repairer's raw text (previously
  discarded) so the controller can inspect it for the dispute marker.
- Added `ParseRepairDispute` (internal, unit tested): extracts the dispute
  reason when present, returns `null` otherwise.

See `docs/PIPELINE_REDESIGN.md` for the full plan and remaining items — next
up is the Plan Gate ⇄ user discussion loop (§三), which needs new UI.
