# AITeam v0.13.0

第七個實作的 `docs/PIPELINE_REDESIGN.md` 項目（§5.2）：目標專案沒有 CI 時，
自動補建，而不是卡住等一個永遠不會出現的檢查結果。

## 這版做了什麼

- **偵測目標專案有沒有 CI**：在建立好隔離工作區、Scout 開始讀專案之前，
  AITeam 會直接檢查目標專案的 `.github/workflows/` 目錄裡有沒有任何檔案。
  這個判斷是用一般程式碼直接檢查檔案系統做的，不是靠 AI 自己判斷——比較
  便宜、也比較不會出錯。
- **順便猜一下技術棧**：同樣用簡單的檔案判斷（有沒有 `.csproj`/`.sln`、
  `package.json`、`requirements.txt`/`pyproject.toml`、`go.mod`、
  `Cargo.toml`），猜測這個專案大概是 dotnet／node／python／go／rust，
  猜不出來就回報「unknown」。
- **沒有 CI 時，Plan Gate 的計畫會自動多一項交付內容**：新增一份最小可用
  的 GitHub Actions workflow（build + test），對應偵測到的技術棧，跟這次
  要做的修改併在同一個任務、同一個 PR 裡完成，不需要另外開一個任務、也
  不需要新的 AI 角色。
- **保底機制**：因為 AITeam 一律用同一個 repo 內的分支（不是 fork）開
  PR，GitHub 通常會直接把 PR 自己新增的 workflow 檔案在這個 PR 上跑起來，
  所以多數情況下這個 PR 本身也能拿到真正的 CI 結果，跟 §5.1 原本的流程
  完全一樣繼續走。但如果等了 2 分鐘後這個 PR 上完全沒有出現任何檢查項目
  （少數 repo 權限限制的情況），**只有這一次**允許跳過 CI 閘門，只靠
  Final Review 把關；下一個任務開始時，CI 已經存在，就會正常照 §5.1 的
  規則走，不會每次都跳過。

## 補充說明

- 新增的三個純邏輯函式（`HasGitHubActionsWorkflows`、
  `DetectTechStackHint`、`NoChecksReported`）都有加上單元測試。
- 這個版本沒有動到 §5.1 已經做好的 PR／CI／風險分級合併流程，只是在它
  前面多加了一層「先確保有 CI 可以跑」的判斷。

到這裡，`docs/PIPELINE_REDESIGN.md` 建議的實作序列（§一到§五）已經全部
做完；後續如果有新的流程改動需求，會再另外討論、寫進規格文件。
